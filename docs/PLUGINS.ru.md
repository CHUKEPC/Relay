# Система плагинов Relay

*[English version](PLUGINS.md)*

> Пишете плагин? Начните с пошагового руководства и примеров в
> [`docs/plugin-guide`](plugin-guide/README.ru.md) ([in English](plugin-guide/README.md)). Этот
> документ описывает архитектуру и модель безопасности, на которых оно построено.

> Статус: **v1 + P1 + P2 — реализовано**. Поверх v1/P1 (кнопки, темы, хуки запроса/ответа,
> панели, хранилище, секретная конфигурация, редактор сетевых хостов, apiVersion): команды
> палитры команд, разрешения `clipboard` + `history:read`, события `workspace`/`collection`,
> ограниченные таймеры в песочнице, интерактивные панели (iframe с нулевым источником + postMessage), переопределение
> подписей через i18n и установка из `.zip` (с ограничением размера; установленные плагины стартуют выключенными).
> Отложенным остаётся только размещённый на сервере подписанный реестр (для него нужна инфраструктура распространения, а не код приложения).

Цель — опыт «модов для Minecraft»: пользователь кладёт папку в каталог плагинов
и получает новые кнопки, темы и автоматизацию — **без форка приложения и
без ослабления базовой безопасности Electron** (`contextIsolation: true`,
`nodeIntegration: false`, `sandbox: true`, никакого сырого Node/`ipcRenderer` даже рядом
со сторонним кодом).

---

## 1. Принципы проектирования

1. **Код плагина никогда не выполняется в рендерере.** Рендерер отрисовывает только *декларативные*
   дополнения (кнопки, темы), прочитанные из манифеста. Весь JavaScript плагинов выполняется
   в изолированном дочернем процессе на стороне главного процесса — по той же усиленной модели, которую
   уже использует песочница скриптов `pm.*` (`src/main/scripting/`).
2. **Возможности, а не всеобъемлющие полномочия.** Плагин получает ровно тот API, который открывают
   *выданные* ему разрешения. Нет разрешения → вызов выбрасывает исключение. Внутри песочницы нет `require`,
   нет `process`, нет Electron, нет IPC (есть только ограниченный `setTimeout`).
3. **Сначала декларативность.** Всё, что нужно UI во время отрисовки (кнопки, темы, схема
   конфигурации), находится в `plugin.json`. Код вызывается только по *событиям* (щелчок по кнопке,
   завершённый ответ), поэтому приложение никогда не выполняет код плагина только ради того, чтобы нарисовать экран.
4. **Отказ в закрытое состояние (fail closed).** Если дочерний процесс песочницы не удаётся запустить или
   ограничения на генерацию кода не действуют, событие отбрасывается с ошибкой — код плагина
   никогда не выполняется с ослабленной изоляцией.
5. **Пользователь — привратник.** Разрешения показываются в «Плагины» простыми фразами на русском о
   последствиях и выдаются явно, когда пользователь включает плагин. Если обновление плагина
   запрашивает *больше* разрешений, плагин выключается до повторного одобрения.

## 2. Архитектура

```
┌────────────────────────── renderer (sandboxed, no Node) ──────────────────────────┐
│  PluginsSection («Плагины»)      ResponsePanel toolbar          Theme engine      │
│  enable/grant/config/delete UI   declarative plugin buttons     plugin themes     │
└─────────────△──────────────────────────△──────────────────────────△──────────────┘
              │ window.api.plugins* (typed IPC, preload contextBridge)
┌─────────────▽──────────────────────────▽─────────────────────────────────────────┐
│ main: PluginManager (src/main/plugins/)                                          │
│  • scans <userData>/relay-data/plugins/*/plugin.json (symlink-confined)          │
│  • validates manifests, merges enable/grant/config state (storage key `plugins`) │
│  • fs.watch hot reload → broadcasts `plugins:event {type:'changed'}`             │
│  • redacts + grant-filters event context, dispatches to the sandbox host         │
└─────────────┬─────────────────────────────────────────────────────────────────────┘
              │ fork() per event — RELAY_PLUGIN_SANDBOX=1, ELECTRON_RUN_AS_NODE=1,
              │ --disallow-code-generation-from-strings, hard wall-clock timeout
┌─────────────▽─────────────────────────────────────────────────────────────────────┐
│ plugin sandbox child (src/main/plugins/sandbox.ts)                                │
│  • node:vm context, codeGeneration disabled, frozen `relay` API                   │
│  • capability-gated: relay.fetch only with `net`, context only with *:read       │
│  • returns { logs, toast, error } — plain JSON only                              │
└───────────────────────────────────────────────────────────────────────────────────┘
```

Один дочерний процесс на событие — точно как в песочнице `pm.*`: зависший или упавший плагин затрагивает
только собственное событие и никогда — приложение или параллельный запуск.

## 3. Устройство плагина

Плагины находятся в каталоге данных приложения:

```
<userData>/relay-data/plugins/
└── webhook-forwarder/          # folder name MUST equal manifest "id"
    ├── plugin.json             # manifest (required, ≤ 64 KB)
    └── main.js                 # handlers (required for code plugins, ≤ 512 KB)
```

Плагин, содержащий только темы, может вообще обойтись без `main.js`. Файлы плагина, являющиеся символическими ссылками, отклоняются,
а любое чтение ограничено папкой плагинов (с проверкой через realpath).

### 3.1 Манифест (`plugin.json`)

```json
{
  "id": "webhook-forwarder",
  "name": "Webhook Forwarder",
  "version": "1.0.0",
  "description": "Posts the current response to a configurable webhook.",
  "author": "you",
  "main": "main.js",
  "permissions": ["net", "request:read", "response:read"],
  "contributes": {
    "buttons": [
      {
        "id": "post-webhook",
        "label": "В webhook",
        "icon": "upload",
        "location": "response-toolbar",
        "tooltip": "Отправить этот ответ в webhook"
      }
    ],
    "themes": [],
    "events": []
  },
  "config": [
    { "key": "webhookUrl", "label": "Webhook URL", "type": "string", "placeholder": "https://hooks.example.com/…" }
  ]
}
```

| Поле | Обязательно | Правила |
|-------|----------|-------|
| `id` | да | `^[a-z0-9][a-z0-9-]{1,63}$`, **должен совпадать с именем папки** (защищает от подмены id; заодно делает дублирующиеся id невозможными) |
| `name` | да | непустое, ≤ 100 символов |
| `version` | да | строка в стиле `x.y.z` |
| `description`, `author` | нет | строки, ≤ 500 / 100 символов |
| `main` | нет | простое имя `.js`-файла внутри папки плагина (без разделителей, без `..`); по умолчанию `main.js` |
| `permissions` | нет | массив значений из §4; неизвестное разрешение ⇒ манифест отклоняется |
| `contributes.buttons` | нет | ≤ 10; `id` — slug, `label` ≤ 40 символов, `location` из §6.1. `icon` — имя иконки Relay; неизвестная иконка НЕ проваливает проверку, вместо неё рисуется значок по умолчанию |
| `contributes.panels` | нет | ≤ 10; `{ id, label, icon?, location: 'response-tab', interactive? }` — вкладка, отрисовывающая HTML в песочнице (§6.3) |
| `contributes.commands` | нет | ≤ 20; `{ id, title, icon? }` — пункты палитры команд (Cmd/Ctrl+K), запускают обработчик `command:<id>` |
| `contributes.themes` | нет | ≤ 10; `{ id, label, base: 'light'\|'dark', vars }`, ≤ 60 переменных в каждой. Ключи должны начинаться с `--`; **значения должны проходить белый список цветов/чисел** (hex, `rgb()/hsl()/oklch()/…`, ключевые слова, простые длины) — всё остальное (например, `url(...)`) отбрасывается (§8) |
| `contributes.events` | нет | массив значений из §5.2 (`response`, `request`, `workspace`, `collection`); для `request` дополнительно требуется разрешение `request:write` |
| `apiVersion` | нет | положительное целое ≤ `PLUGIN_API_VERSION` приложения (сейчас 1); большее значение приводит к отказу, поэтому старые версии приложения отклоняют плагины из будущего |
| `config` | нет | ≤ 20 полей; `{ key, label, type: 'string'\|'secret', placeholder?, description? }`. Значения `secret` хранятся в safeStorage (задаются через «Плагины» → `setSecret`), никогда не хранятся в документе и не отправляются рендереру в открытом виде |
| `i18n` | нет | `{ locale: { key: value } }`; подпись/заголовок/описание, записанные как `%key%`, заменяются значением для языка приложения (по умолчанию `ru`) |

Ошибки проверки никогда не роняют приложение: сломанный плагин отображается в «Плагины» с
текстом ошибки, и его нельзя включить.

### 3.2 Модуль обработчиков (`main.js`)

Обычный скрипт, который выполняется один раз на каждое событие внутри песочницы. Он регистрирует обработчики через
глобальный объект `relay`:

```js
relay.on('button:post-webhook', async (ctx) => {
  const url = relay.config.webhookUrl
  if (!url) return relay.toast('Укажите Webhook URL в настройках плагина', 'error')
  if (!ctx.response) return relay.toast('Сначала отправьте запрос', 'error')

  const res = await relay.fetch(url, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      request: ctx.request,                  // requires request:read
      status: ctx.response.status,           // requires response:read
      body: ctx.response.bodyText
    })
  })
  relay.toast(res.ok ? `Отправлено (${res.status})` : `Webhook ответил ${res.status}`, res.ok ? 'ok' : 'error')
})
```

Контракт для авторов:

- **Между событиями никакое состояние не сохраняется** — каждый вызов идёт в новом процессе. Для постоянного
  состояния используйте разрешение `storage` (`relay.storage.*`, хранилище ключ-значение в пределах плагина).
- **Возвращаемые значения обработчиков зарезервированы** (под будущую семантику изменения запроса). Возвращайте
  `undefined`; всё остальное приводит к предупреждению на карточке плагина.
- **Приоритет обработчиков кнопок**: специфичный обработчик `button:<id>` побеждает; общий обработчик
  `button` выполняется, только если специфичный не зарегистрирован.
- Отклонение промиса, *возвращённого* обработчиком, становится ошибкой запуска; отсоединённые
  «висящие» промисы не отслеживаются.

## 4. Модель разрешений

Разрешения объявляются в манифесте и **выдаются пользователем** при включении
плагина. Выданные разрешения сохраняются в документе хранилища уровня приложения `plugins.json` рядом с
состоянием включения и значениями конфигурации.

| Разрешение | Текст в UI (RU) | Что даёт | Примечания |
|------------|--------------|--------|-------|
| `net` | «Доступ в интернет — любой хост» | `relay.fetch` к любому хосту | всё или ничего, **и редиректы намеренно не ограничиваются**; 10 с на вызов, ≤ 5 вызовов на событие, ответ до 1 МБ, ≤ 5 переходов по редиректам |
| `net:<host>` | «Доступ в интернет — только `<host>`» | `relay.fetch`, ограниченный этим хостом (точное имя или `*.suffix`, при необходимости `:port` — сравнивается с фактическим портом, поэтому `net:example.com:443` соответствует `https://example.com/`) | можно указывать несколько раз; проверяется на **каждом переходе редиректа**, а не только для исходного URL; простой `net` снимает ограничение |
| `request:read` | «Чтение запроса (секретные заголовки скрыты)» | замаскированный снимок запроса в контексте события | значения заголовков, подходящих под `CREDENTIAL_HEADER_RE` движка, маскируются; userinfo из URL удаляется, а значения **всех** query-параметров маскируются (ключи сохраняются) |
| `response:read` | «Чтение ответа (тело до 200 КБ)» | снимок ответа в контексте события | статус, заголовки (с тем же маскированием), текстовое тело до 200 КБ, тайминги, размер |
| `request:write` | «Изменение запроса перед отправкой» | `relay.request.*` в обработчике `request` | операции с заголовками — по имени (set/remove) + url/method; обязательно для объявления события `request` |
| `storage` | «Своё хранилище данных» | `relay.storage.*` (KV-хранилище в пределах плагина) | снимок на входе / изменения на выходе; ≤ 100 ключей, ≤ 8 КБ на значение; хранится ВНЕ папки плагина |
| `clipboard` | «Запись в буфер обмена» | `relay.clipboard.writeText` | текст, который плагин просит скопировать, записывает main (≤ 100 КБ) |
| `history:read` | «Чтение истории запросов» | недавняя история в `ctx.history` | сначала новые, ≤ 25 записей, URL замаскированы (значения query скрыты) |

Секретная конфигурация (`type: 'secret'`) хранится в safeStorage: значения записываются через
«Плагины» → `setSecret`, хранятся под ключом `plugin:<id>:<key>`, никогда не отправляются рендереру в
открытом виде и подставляются в `relay.config` только внутри песочницы в момент вызова.

Жизненный цикл выданных разрешений:

- **Включить = выдать.** При включении плагина записывается `granted = manifest.permissions` на
  этот момент. Если разрешения перечислены, переключатель подписан «Включить и разрешить».
- **Расширение разрешений ⇒ повторное одобрение.** При каждом вызове менеджер заново проверяет
  `manifest.permissions ⊆ granted`. Если манифест после горячей перезагрузки просит больше, плагин
  выключается, а карточка показывает **разницу — вновь запрошенные разрешения**, пока
  пользователь не включит его снова.
- **Удаление папки отменяет активацию.** Запись состояния, чья папка исчезла, получает
  `enabled: false, granted: []` (конфигурация сохраняется) — повторная установка с тем же id начинается в выключенном
  состоянии и требует повторного одобрения. *Выключение* сохраняет выданные разрешения и конфигурацию; *«Удалить»* (деинсталляция)
  удаляет папку и стирает запись.
- **Сужение сети до отдельных хостов.** Для плагина, получившего широкое `net`, на карточке в «Плагины» есть
  редактор списка разрешённых хостов; непустой список заменяет `net` ровно этими записями
  `net:<host>` в момент вызова (строгое сужение — он никогда не расширяет выданное).
- Возможности проверяются **дважды**: главный процесс удаляет и маскирует контекст, на который у плагина
  нет разрешения, *до* границы форка, а песочница отказывает в вызовах API, на которые
  разрешения не выдано.

Разрешение не требуется для: `relay.toast`, `relay.log/info/warn/error`,
`relay.config` (собственная конфигурация), получения `buttonId`.

## 5. Модель выполнения и жизненный цикл

### 5.1 Песочница

Каждый вызов события запускает форком `out/main/sandbox.js` — бандл песочницы (`src/main/sandbox-entry.ts`),
а не бандл приложения, который выполнил бы `require('electron')` и упал в собранном приложении, — со следующим:

- `RELAY_PLUGIN_SANDBOX=1` → форк запускает `startPluginSandboxHost()` вместо хоста скриптов;
- `ELECTRON_RUN_AS_NODE=1` → чистый Node, без Chromium;
- `--disallow-code-generation-from-strings` → `eval`/`new Function` не работают, а это
  единственный известный вектор выхода из `node:vm`. Дочерний процесс сам проверяет этот флаг и **отказывается
  работать (fail closed)**, если флаг не действует (так же, как `src/main/scripting/index.ts`).

Внутри дочернего процесса `main.js` выполняется через `runInContext` в контексте, созданном с
`codeGeneration: { strings: false, wasm: false }`, где единственные глобальные объекты — **замороженный**
API `relay` и перехватывающий вывод `console`. Возвращаемые данные проходят через сериализацию в JSON и обратно, поэтому функции
и объекты хоста не могут утечь наружу.

Ограничения (константы в `src/main/plugins/host.ts` / `sandbox.ts`):

| Предел | Значение |
|-------|-------|
| синхронное выполнение | 3 с (таймаут `vm`) |
| завершение асинхронного обработчика | 10 с |
| жёсткий предел по реальному времени (дочерний процесс уничтожается) | 15 с |
| параллельные песочницы плагинов | 2 (щелчки по кнопкам ставятся в очередь; хуки схлопываются, см. §5.2) |
| размер `main.js` | 512 КБ |
| `relay.fetch` | 5 вызовов на событие; 10 с и ≤ 5 переходов по редиректам на вызов; ответ ≤ 1 МБ |

### 5.2 События

| Событие | Когда срабатывает | Ключ обработчика | Контекст |
|-------|-----------|-------------|---------|
| щелчок по кнопке | пользователь нажимает кнопку, добавленную плагином | `button:<buttonId>` (запасной: `button`) | `{ buttonId, request?, response? }` |
| `response` | HTTP-движок завершил запрос (объявляется через `contributes.events: ["response"]`) | `response` | `{ request?, response? }` |
| `request` | перед отправкой, БЛОКИРУЮЩЕЕ (объявляется через `contributes.events: ["request"]`, нужно `request:write`) | `request` | `{ request? }` |
| отрисовка панели | вкладка панели открыта/обновлена (или интерактивная панель отправила сообщение) | `panel:<panelId>` (запасной: `panel`) | `{ panelId, request?, response?, message? }` |
| команда | пользователь запускает добавленную плагином команду из палитры (Cmd/Ctrl+K) | `command:<commandId>` (запасной: `command`) | `{ commandId, request?, response? }` |
| `workspace` | сменилось активное рабочее пространство (`contributes.events: ["workspace"]`) | `workspace` | `{ workspace }` |
| `collection` | изменился документ коллекций (`contributes.events: ["collection"]`) | `collection` | `{}` (+ история, если есть разрешение) |

Хук `request` выполняется последовательно перед отправкой и может изменить разрешённую спецификацию через
`relay.request.*`, поэтому он **действительно блокирует отправку** (в этом и смысл — он меняет
запрос). Чтобы это оставалось в рамках, у каждого хука запроса короткий собственный таймаут (5 с против
15 с для событий без ожидания результата): медленный/зависший плагин уничтожается и пропускается, а не
задерживает отправку, а отмена запроса прерывает оставшиеся хуки. **Безопасность:** хук
может свободно переписывать запрос **в пределах источника (origin) пользователя**, но перенаправление на ДРУГОЙ
источник выполняется, только если у плагина есть `net`/`net:<host>` для нового хоста (та же
проверка, что и у `relay.fetch`), — иначе замена URL отклоняется и запрос сохраняет
исходный URL. Даже при разрешённом перенаправлении на другой источник авторизация пользователя, заголовки с учётными данными,
тело и строка запроса удаляются (см. §8), поэтому `request:write` никогда не может переслать
секреты пользователя (в авторизации, заголовке, теле или query-параметре) на другой хост; плагин,
которому нужно сделать POST на другой источник, передаёт собственное тело и использует собственное разрешение `net`.

События `workspace` и `collection` работают без ожидания результата (с тем же схлопыванием, что и
`response`): `workspace` срабатывает при смене активного рабочего пространства (`ctx.workspace`),
`collection` — при сохранении документа коллекций.

Хук `response` вызывается **из главного процесса без ожидания результата** после
завершения `request:send` — он работает и для ручной отправки, и для раннера коллекций и
никогда не может задержать или сорвать сам запрос (вызов вынесен за пределы пути IPC-ответа,
а запросы, отменённые пользователем, пропускаются; транспортные сбои со `status: 0`
ПЕРЕДАЮТСЯ в хук — плагинам оповещения они нужны). Он **намеренно работает по мере возможности и с потерями**:
для каждого плагина одновременно выполняется не более одного запуска и сохраняется только *последнее*
ожидающее событие (схлопывание «побеждает последнее»), поэтому запуск коллекции не может наплодить дочерних процессов. Плагины
не должны рассчитывать на получение каждого ответа.

Наблюдаемость (средства отладки v1):

- запуск хука, завершившийся ошибкой (и не показавший уведомления), вызывает **подписанное** уведомление
  об ошибке — «Плагин `<name>`: `<error>`» — с дедупликацией по плагину (одинаковые уведомления в течение
  10 с отбрасываются);
- результат каждого запуска (`lastRun`: отметка времени, событие, длительность, ошибка, хвост журнала) показывается
  на карточке плагина в «Плагины», отправляется точечной рассылкой
  `plugins:event {type:'lastRun'}` и объединяется на стороне клиента (полная перезагрузка по `changed`
  здесь пересканировала бы папку на каждый запуск и затирала бы поля конфигурации прямо во время ввода);
- журналы запусков по кнопкам дополнительно попадают в консоль devtools рендерера.

### 5.3 Горячая перезагрузка

`PluginManager` следит за каталогом плагинов одним рекурсивным `fs.watch`
(поддерживается на macOS/Windows/Linux в текущем Electron). После ошибок наблюдателя папка создаётся заново
и наблюдение возобновляется. Изменения обрабатываются с задержкой (debounce, 300 мс), кэш сканирования сбрасывается,
а рендерер получает `plugins:event {type:'changed'}` и обновляется. Кнопка «Обновить»
(и любой вызов `plugins:list`) всегда принудительно запускает новое сканирование — запасной выход на случай
пропущенного события наблюдателя. `main.js` читается с диска в момент вызова, поэтому правки кода вступают в силу
с самого следующего события.

## 6. Точки расширения

### 6.1 Кнопки

`contributes.buttons[].location`:

| Расположение | Где отображается | Статус |
|----------|------------------|--------|
| `response-toolbar` | ряд действий в строке состояния ответа (рядом с «Спросить AI») | **готово** |
| `titlebar` | слева от плашки окружения (компактная кнопка-иконка) | **готово** |
| `sidebar` | подвал боковой панели, над «Консоль» | **готово** |

Кнопки в заголовке окна и на боковой панели действуют на запрос АКТИВНОЙ вкладки и его текущий ответ (их собирает
рендерер, а main повторно фильтрует по выданным разрешениям).

Строка состояния не переносится (а в режиме разделения делится пополам), поэтому **в строке отображается не более 3 кнопок
плагинов** суммарно по всем плагинам (в порядке id плагина); остальные сворачиваются
в меню переполнения «⋯». Пока событие выполняется, кнопка неактивна и показывает индикатор загрузки.
Каждый щелчок заметно завершается: уведомлением с результатом, уведомлением об ошибке или подписанным
«готово» — всё это отрисовывает доверенная оболочка приложения в виде «Плагин `<name>`: …».

Щелчок по кнопке вызывает плагин со снимком запроса/ответа активной вкладки
(отфильтрованным по разрешениям и замаскированным в main — копия рендерера служит лишь вспомогательными входными данными).

### 6.2 Темы

Темы, добавляемые плагинами, — это **чистые данные**: они проверяются при разборе манифеста (ключи должны быть
пользовательскими свойствами `--`, значения должны проходить белый список цветов/чисел) и применяются через
существующий механизм пользовательских тем. «Применить» на карточке плагина выполняет один вызов
`useSettings.update({ themePreset: 'custom', customTheme })` с **указанием происхождения**
(`customTheme.source = { pluginId, themeId }`) и сохраняет прежнее оформление пользователя
в `SettingsDoc.appearanceSnapshot` (только если перезаписывается собранная вручную тема, так что при
последовательном применении тем плагинов сохраняется исходная резервная копия). Кнопка применённой темы превращается в
«Вернуть прежнюю», которая восстанавливает снимок. Скопированная тема переживает удаление
плагина — ничего не ломается, она просто становится пользовательской темой.

### 6.3 Панели

Элемент `contributes.panels[]` (`location: 'response-tab'`) добавляет вкладку в панель
ответа. Открытие/обновление вкладки вызывает событие `panel:<id>`; обработчик строит HTML
через `relay.panel.set(html)`, а рендерер показывает этот HTML в **полностью изолированном
`<iframe>`** (`sandbox=""`, CSP `default-src 'none'; img-src data:; style-src
'unsafe-inline'`) — без скриптов, без удалённых загрузок, по той же модели, что и HTML-предпросмотр ответа.
Рендерер никогда не выполняет JS плагина в собственном контексте; данные панели формирует
обработчик в песочнице. Кнопка «Обновить» перезапускает обработчик.

**Интерактивные панели** (`interactive: true`): iframe отрисовывается с
`sandbox="allow-scripts"`, но **без** `allow-same-origin`, поэтому у него *нулевой источник (null origin)* — его
скрипт не может добраться до приложения, cookie, хранилища или сети (CSP по-прежнему блокирует
`default-src`); он может только вызывать `parent.postMessage(...)`. Рендерер пересылает это сообщение
в обработчик плагина `panel:<id>` как `ctx.message`; какой бы HTML обработчик затем ни задал, он
перерисует iframe. Это единственное место, где разметка, созданная плагином, может выполнять скрипты,
и только внутри этого замкнутого фрейма с нулевым источником.

### 6.4 Команды

`contributes.commands[]` добавляет пункты в палитру команд (Cmd/Ctrl+K, группа
«Плагины»). Выбор пункта запускает обработчик `command:<id>` с контекстом запроса/ответа
активной вкладки (отфильтрованным по разрешениям в main).

## 7. API времени выполнения (`relay.*`)

Доступен внутри `main.js` (замороженный объект, единственный глобальный объект помимо `console`; в песочнице
**нет таймеров** — только микрозадачи):

| Член | Разрешение | Описание |
|--------|-----------|-------------|
| `relay.on(event, fn)` | — | зарегистрировать обработчик; для каждого ключа события побеждает последняя регистрация |
| `relay.config` | — | замороженный `Record<string,string>` со значениями конфигурации пользователя |
| `relay.toast(message, kind?)` | — | поставить уведомление в очередь (`'ok'` \| `'error'`, ≤ 300 символов); побеждает последнее; отображается от имени плагина |
| `relay.log/info/warn/error(...)` | — | перехватываемые строки консоли (также `console.*`); хвост показывается на карточке плагина |
| `relay.fetch(url, init?)` | `net` / `net:<host>` | голый fetch (без хранилища cookie / прокси / сертификатов приложения), `init = { method?, headers?, body? }` |
| `relay.storage.get/has/set/delete/keys` | `storage` | KV-хранилище в пределах плагина (строковые значения); изменения записываются, и после запуска main их сохраняет |
| `relay.request.setUrl/setMethod/setHeader/removeHeader` | `request:write` | изменить запрос в обработчике `request` (операции с заголовками — по имени) |
| `relay.panel.set(html)` | — | задать HTML в обработчике `panel:<id>` (отрисовывается в изолированном iframe) |
| `relay.clipboard.writeText(text)` | `clipboard` | скопировать текст в буфер обмена ОС (записывается main после запуска) |
| `setTimeout` / `clearTimeout` | — | ограниченные таймеры (≤ 50 активных, ≤ 5 с каждый); все сбрасываются по окончании запуска, поэтому `await new Promise(r => setTimeout(r, ms))` подходит для коротких задержек |

`relay.fetch` возвращает объект в форме ответа `pm.sendRequest` (он никогда не пересекает границу
форка, поэтому методы допустимы):

```ts
{
  ok: boolean
  status: number
  statusText: string
  truncated: boolean                        // body was cut at the 1 MB cap
  headers: { get(name): string | undefined  // case-insensitive
             all(): Record<string, string> } // lowercase keys
  text(): string
  json(): unknown                           // JSON.parse — throws on invalid
}
```

Семантика отказов (контракт):

- таймаут ⇒ отклонение с `relay.fetch: timed out after 10s` (охватывает всю цепочку редиректов);
- редирект на хост без разрешения ⇒ отклонение с `relay.fetch: redirected to a host not
  allowed…` **до** отправки запроса на этом переходе; > 5 переходов ⇒ `too many redirects`;
- 6-й вызов в рамках одного события ⇒ отклонение (`at most 5 calls per event`);
- тело сверх лимита НЕ приводит к отклонению — оно усекается с `truncated: true`;
- заголовки запроса, похожие на учётные данные, удаляются при переходах на другой источник (тот же
  `CREDENTIAL_HEADER_RE`, что и в HTTP-движке); 301/302/303 понижают метод до GET и отбрасывают
  тело, 307/308 сохраняют и то и другое.

Контекст события (`ctx`): `buttonId?` / `panelId?` (для событий кнопок/панелей), `request?`
(`{ method, url, headers }`, замаскированный), `response?` (`{ status, statusText, headers,
contentType, bodyText?, truncated?, sizeBytes, timeMs, finalUrl }`, с ограничениями). Обработчики могут
быть `async`; запуск завершается, когда возвращённый промис завершится или истекут 10 с.

Операции с заголовками `relay.request.*` (request:write) применяются к разрешённой спецификации *до* того, как
движок подставит авторизацию уровня спецификации, поэтому заголовок, который также формирует настройка авторизации запроса (например,
`Authorization` для авторизации `bearer`), перезаписывается этой настройкой — авторизация пользователя побеждает. Чтобы
полностью управлять заголовком, установите для авторизации запроса значение «None».

## 8. Модель безопасности

Модель угроз: плагин — это **недоверенный сторонний код** (скачанный из интернета,
присланный другом). Рендерер и главный процесс — доверенный код приложения.

Чего плагин **не может** сделать — по построению:

| Атака | Защита |
|--------|---------|
| добраться до API Node / Electron | контекст `node:vm` только с `relay` + `console`; генерация кода отключена на уровне процесса (`--disallow-code-generation-from-strings`) **и** на уровне контекста; при провале самопроверки дочерний процесс отказывается работать |
| затронуть DOM рендерера / `ipcRenderer` | JS плагина никогда не попадает в рендерер; UI-дополнения — это статический JSON, отрисовываемый доверенными компонентами |
| прочитать API-ключи / секреты safeStorage | дочерний процесс песочницы получает только: код плагина, выданные разрешения, СОБСТВЕННУЮ конфигурацию плагина (включая его СОБСТВЕННЫЕ расшифрованные секретные поля), его СОБСТВЕННОЕ KV-хранилище и замаскированный контекст события. Секреты приложения, ключи AI-провайдеров, расшифрованное хранилище секретов и данные других плагинов никогда не пересекают границу форка |
| отрисовать панель, которая выполняет скрипты / «звонит домой» | неинтерактивные панели: `<iframe sandbox="">` + CSP `default-src 'none'` (без скриптов, без удалённых загрузок). **Интерактивные** панели: `sandbox="allow-scripts"` БЕЗ `allow-same-origin` → нулевой источник (нет доступа к приложению, cookie, хранилищу), и CSP по-прежнему блокирует всю сеть; iframe может только отправлять `postMessage` приложению |
| прочитать буфер обмена ОС / засорить его | `relay.clipboard` — ТОЛЬКО для записи (`writeText`), требует разрешения `clipboard`, ограничен 100 КБ, а запись выполняет main |
| выуживать данные из истории запросов | `history:read` открывает только ≤ 25 самых свежих записей (метод/url/статус/тайминги), URL замаскированы (значения query скрыты) — никогда не тела и не заголовки |
| атаковать через `installZip` | ограничены и сжатый, И распакованный размер (защита от zip-бомб через пофайловый фильтр fflate); манифест полностью проверяется; id привязан к целевой папке; каждый элемент записывается, только если его путь остаётся внутри `plugins/<id>/` (никаких выходов через `..`/абсолютные пути/символические ссылки/за пределы префикса); и только что установленный плагин ВСЕГДА стартует **выключенным и без выданных разрешений** — даже при перезаписи доверенного плагина с тем же id, — поэтому подменённый код никогда не выполнится со старыми разрешениями без повторного одобрения. (Никаких заявлений о подписи/«проверенности» не показывается: подпись внутри архива ничего не доказывает без закреплённого якоря доверия — для этого нужен размещённый на сервере реестр, §11.) |
| хранить данные сверх квоты / выйти за пределы своего хранилища | `relay.storage` — отдельное KV-хранилище для каждого плагина (≤ 100 ключей, ≤ 8 КБ на значение): main передаёт внутрь его снимок и применяет изменения снаружи; оно хранится ВНЕ папки плагина, поэтому плагин не может напрямую переписать собственный файл состояния |
| внедрить вредоносный запрос через `request:write` | через границу проходят только упорядоченные операции set/remove заголовков по имени + операции url/method (замаскированный набор заголовков никогда не передаётся обратно); они применяются к разрешённой спецификации в main |
| увести авторизацию/тело/query пользователя на другой хост, подменив URL через `request:write` | перенаправление на другой источник **отклоняется, если у плагина нет `net`/`net:<host>` для нового хоста** (та же проверка, что и у `relay.fetch`), — поэтому хук запроса никогда не даёт больше охвата, чем у плагина уже есть; в противном случае запрос пользователя сохраняет исходный URL. Даже при разрешённом перенаправлении на другой источник авторизация пользователя (`spec.auth`), заголовки с учётными данными (`CREDENTIAL_HEADER_RE`), **тело** запроса и **строка запроса** удаляются перед отправкой, поэтому приложение никогда не пересылает секреты пользователя на другой источник; плагин делает POST на другой источник только через `relay.fetch` с собственным разрешением `net` и собственным телом |
| застопорить каждый запрос зависшим хуком `request` | хук перед отправкой ограничен таймаутом 5 с на хук (против 15 с для событий без ожидания результата); медленный плагин уничтожается и пропускается, а отмена запроса прерывает оставшиеся хуки |
| украсть учётные данные из снимка | значения заголовков, подходящих под `CREDENTIAL_HEADER_RE` движка, маскируются; в URL (включая `finalUrl` после авторизации) userinfo удаляется, **фрагмент отбрасывается** (`#access_token=…` из implicit flow OAuth никогда не доходит до плагина) и маскируется **каждое** значение query — а не угадываемые по имени, — поэтому авторизация движка с apikey в query (имя параметра выбирает пользователь) не может утечь; `CREDENTIAL_HEADER_RE` общий с движком, поэтому маскирование заголовков и их удаление при редиректах не могут разойтись. **Оговорка (честно о границах):** маскирование опирается на ИМЕНА заголовков и на значения в URL; секрет, который пользователь помещает в заголовок с нестандартным именем или в тело ответа, ВИДЕН плагину, получившему `request:read`/`response:read`, — в этом и смысл разрешения, и диалог выдачи разрешений прямо об этом говорит. Считайте, что такие разрешения означают «этот плагин может читать данные моего запроса/ответа». |
| вынести данные без согласия | доступ к сети требует выданного пользователем разрешения `net`; `net:<host>` перепроверяется на **каждом переходе редиректа** до отправки запроса |
| вынести данные через CSS темы (маячки `url(...)`) или подделать доверенную оболочку | значения переменных темы должны проходить белый список цветов/чисел на этапе проверки манифеста; отклонённые значения никогда не сохраняются. (Эшелонированная защита: CSP рендерера и так блокирует удалённые `img-src`/`font-src`.) |
| подвесить приложение или устроить DoS | отдельный дочерний процесс на событие, жёсткое уничтожение через 15 с, не более 2 параллельных процессов, схлопывание хуков (≤ 1 выполняющийся + 1 ожидающий на плагин), ограничения на fetch/ответ/тело/журнал |
| выбраться за пределы через `plugin.json` / символические ссылки | строгая проверка манифеста; `main` не может содержать разделителей; файлы плагина читаются с проверкой lstat (символические ссылки отклоняются) и ограничением папкой плагинов через realpath; `installSample` отказывается работать с целями, являющимися символическими ссылками |
| выдать себя за другой плагин | имя папки должно совпадать с `id` в манифесте; авторство уведомлений указывает доверенная оболочка, а не плагин |
| тихо расширить разрешения при обновлении | `granted` — это снимок; любое требование сверх него выключает плагин до повторного одобрения, с показом разницы; удалённая, а затем заново установленная папка стартует выключенной |

Остаточные риски (задокументированы и приняты для v1):

- выданное простое разрешение `net` позволяет отправить (уже замаскированный) контекст
  куда угодно — ровно это пользователь и одобрил; `net:<host>` — инструмент для ограничения охвата;
- DNS rebinding для разрешённого хоста не предотвращается (в v1 нет привязки к разрешённому IP-адресу);
- маскирование заголовков основано на именах — заголовок с нестандартным, не подпадающим под шаблон именем (например, `X-Session`)
  проходит как есть; значения query маскируются полностью, но секрет, встроенный в **путь** URL,
  всё равно проходит; разрешения, ограниченные хостами, снижают риск утечки;
- само тело ответа может содержать секреты, которые вернул сервер, и никакой клиент не может
  отличить их от данных.

## 10. Комплекты возможностей (встроенные, декларативные)

Наряду с описанной выше системой пользовательских плагинов Relay поставляет **комплекты возможностей** в папке `plugins/`
рядом с исполняемым файлом (`extraResources`; при разработке — корень репозитория). Они
определяют, чем приложение *является*, а не расширяют его кодом:

```
plugins/
├── websocket/plugin.json          → protocol.websocket
├── sse/plugin.json                → protocol.sse
├── socketio/plugin.json           → protocol.socketio
├── mqtt/plugin.json               → protocol.mqtt
├── grpc/plugin.json               → protocol.grpc
├── ai-assistant/plugin.json       → ai
├── advanced-auth/plugin.json      → auth.advanced
├── extra-panes/plugin.json        → panes.extra
├── backup-formats/plugin.json     → backup.extra
├── codegen-languages/plugin.json  → codegen.extra
├── script-snippets/
│   ├── plugin.json                → snippets
│   └── snippets.json
├── theme-pack/
│   ├── plugin.json                → themes.extra
│   └── themes.json
└── extra-languages/
    ├── plugin.json                → i18n.extra
    └── locales/{de,es}.json
```

Базовое приложение без единого комплекта — это: HTTP + GraphQL, шесть распространённых схем авторизации
(inherit / no auth / Bearer / Basic / API key / OAuth 2.0), русский и английский языки и до
четырёх панелей.

**Почему отдельный механизм.** Пользовательский плагин — это недоверенный код, и он выполняется в песочнице с
выданными разрешениями. Комплект возможностей ничего не выполняет — это манифест (плюс JSON с локалями
для языков), поэтому ему не нужны ни песочница, ни диалог согласия. Удаление его папки полностью убирает
возможность; переключатель в Настройки → Плагины лишь скрывает её.

**Комплект в папке — ещё не комплект в приложении.** Список в настройках показывает только те комплекты,
которые пользователь действительно взял в приложение, — отмеченные в установщике или выбранные позже через «Выбрать
плагин на компьютере…». Остальные просто лежат в `plugins/`, невидимые, пока их не добавят.
Удаление комплекта работает наоборот: он пропадает из списка, и его возможность исчезает, но
его папка остаётся на месте, так что комплект, поставляемый с приложением, всегда можно добавить снова без
переустановки.

| Элемент | Где |
|---|---|
| список возможностей + типы манифеста | `src/shared/features.ts` |
| сканирование папки, состояние, чтение локалей, IPC | `src/main/features/index.ts` |
| стор рендерера + `useCap()` | `src/renderer/store/features.ts` |
| UI настроек | `src/renderer/features/settings/FeaturePacks.tsx` |
| движок перевода | `src/renderer/lib/i18n.ts`, `src/renderer/locales/en.json` |
| файлы данных сниппетов / тем: разбор, белый список цветов, варианты | `src/shared/pack-data.ts` (покрыт модульными тестами на встроенных комплектах) |
| применение тем, палитра Monaco | `src/renderer/store/settings.ts`, `src/renderer/lib/monaco.ts` |

Комплекты **включаются явно (opt-in)**: комплект, который ни разу не включали, остаётся выключенным, поэтому свежая установка —
это базовое приложение и ничего больше. Установщик для Windows спрашивает, какие комплекты включить, и записывает
ответ в `install-config.json` рядом с исполняемым файлом; `src/main/features/install.ts` применяет его
один раз на установку (маркером служит mtime файла) и также переносит язык установщика
в `settings.language`. Повседневные переключения в Настройки → Плагины никогда не перезаписываются.

Состояние включения/выключения хранится в документе уровня приложения `features`.

Комплекты не ограничены теми, что поставляются с приложением: **Настройки → Плагины → «Выбрать
плагин на компьютере…»** принимает `plugin.json` (или содержащий его `.zip`) из любого места на
диске, проверяет его и копирует в папку плагинов уже включённым. Диалог открывается в
папке плагинов — так же в работу берётся и поставляемый, но не выбранный комплект: выбор
папки, которая уже там лежит, добавляет её без какого-либо копирования. Элементы архива с абсолютными
путями или сегментами `..` отбрасываются, а id в манифесте должен быть простым токеном, поэтому архив
никогда не может записать что-либо за пределами собственной папки (`src/main/features/pack-source.ts`, покрыто модульными тестами).

Для обоих видов есть один диалог выбора: `features:install` владеет диалогом, а архив, который
не является комплектом возможностей, передаётся установщику плагинов с кодом, поэтому пользователю никогда не нужно знать,
какой вид он выбрал. Экран настроек точно так же показывает комплекты и плагины с кодом в одном списке,
и в каждой строке есть имя, всплывающее окно с информацией (описание, что добавляет, разрешения, папка) и
элементы управления удалением/включением.

## 11. Дорожная карта

Все изначально отложенные пункты P1 **и P2** реализованы: секретная конфигурация, `storage`,
`request:write`, панели, кнопки в заголовке окна и на боковой панели, редактор разрешений по хостам, `apiVersion`,
команды палитры команд, `clipboard` + `history:read`, события `workspace`/`collection`,
ограниченные таймеры в песочнице, интерактивные (postMessage) панели, переопределение подписей через i18n и
установка из `.zip` (с ограничением размера; только что установленные плагины стартуют выключенными).

Что действительно осталось (нужна инфраструктура распространения, а не код приложения):

- **Размещённый на сервере реестр / маркетплейс плагинов с подписью** — сервер, который хранит плагины и
  подписывает их ключами, ЗАКРЕПЛЁННЫМИ как доверенные в поставляемом приложении. Установка из `.zip` работает уже сейчас, но
  *осмысленная* проверка подписи требует этой схемы с закреплёнными ключами/реестром (самоподписанный
  архив ничего не доказывает), а это решение уровня продукта/инфраструктуры — не то, что десктопное
  приложение может «доделать» офлайн. Сознательно НЕ имитируется самоподписью внутри архива.
